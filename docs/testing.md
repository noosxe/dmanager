# Testing Strategy & Guidelines

This document outlines the testing strategy for the Docker Container Manager web application, focusing on unit testing, mocking patterns, database testing, and continuous integration rules.

---

## 1. Backend Testing (Go)

The Go backend prioritizes testability by leveraging explicit Dependency Injection (DI) and clean interfaces.

### 1.1. Testing Framework & Assertions
* **Standard Library:** All unit tests use Go's native `testing` package (`*_test.go` files).
* **Assertions:** We utilize **`github.com/stretchr/testify`** (specifically `assert` and `require`) to provide clean, readable error reporting.
  * Use `require` for setup assertions that should abort the test immediately if they fail (e.g., database connection setups).
  * Use `assert` for validation checks that can fail without halting subsequent checks in the same test.

### 1.2. Mocking Strategy
* **Interface Mocks:** Because backend packages communicate through interfaces, dependencies are mocked at boundary levels.
* **Mock Generation (`mockery`):** We use **`github.com/vektra/mockery`** to automatically generate type-safe mock implementations for internal interfaces. Mock generation configs are defined in `.mockery.yaml`.
* **Example Pattern:**
  * When testing a service (e.g., `ContainerService`), we inject a mock `DockerClient` (generated by mockery) to isolate the service logic from physical Unix socket Docker operations.

### 1.3. Database Testing (SQLite)
* **Real Integration Database:** Rather than mocking the SQL database driver or ORM layer, we run query-level tests against a real **SQLite in-memory database (`:memory:`)**.
* **Flow:**
  1. Open a new SQLite in-memory connection for each test suite.
  2. Run embedded Goose migrations against the in-memory instance to build the schema.
  3. Instantiate the SQLC-generated queries struct using the test database.
  4. Perform queries and verify data state changes.
* This approach ensures SQL queries generated by SQLC are validated against actual SQLite syntax without mocking overhead.

### 1.4. ConnectRPC Endpoint Testing
* **In-Memory Testing Server:** ConnectRPC handlers are standard HTTP handlers and can be tested using Go's standard `net/http/httptest` package.
* **Flow:** Spin up a local `httptest.NewServer` hosting the Connect handlers, instantiate the generated Connect client pointing to this local server, and run client-side calls to verify endpoints, middleware, and interceptors.

## 2. Frontend Testing (React)

The React SPA utilizes modern web testing utilities optimized for the Vite/TS ecosystem.

### 2.1. Testing Framework (Vitest)
* **Vitest Runner:** We use **Vitest** as the primary test runner because it reuses Vite's configuration and module resolution, providing extremely fast execution speeds.
* **Linting Validation:** Oxlint and Oxfmt run checks via `pnpm check` to verify formatting and lint standards before tests run.

### 2.2. Component & DOM Testing (React Testing Library)
* **React Testing Library (RTL):** Used to mount and test React components. Testing focuses on user interactions (clicks, text input, keyboard navigation) rather than implementation details.
* **DOM Assertions:** Enabled via `@testing-library/jest-dom` for custom assertions (e.g., `toBeInTheDocument()`, `toBeDisabled()`).

### 2.3. Mocking ConnectRPC & TanStack Query
* **Query Hook Mocking:** For component tests, we wrap components in a test `QueryClientProvider` and mock the response functions of the generated ConnectRPC TypeScript client.
* **Network Mocking (MSW):** For integration tests, we utilize **Mock Service Worker (MSW)** to intercept HTTP calls matching the ConnectRPC routes, returning mock Protobuf payloads to check complete frontend data pipelines.

## 3. Test Command Execution

Developers run tests within the local Nix environment to ensure library compatibility.

### 3.1. Backend Commands
* **Run All Tests:**
  ```bash
  nix develop --command go test -v -race ./...
  ```
* **Generate Mocks:**
  ```bash
  nix develop --command mockery
  ```

### 3.2. Frontend Commands
* **Run All Tests (Single Run):**
  ```bash
  nix develop --command pnpm test
  ```
* **Run Tests in Watch Mode:**
  ```bash
  nix develop --command pnpm vitest
  ```

---

## 4. Continuous Integration (CI)

* CI runners run tests natively (without Nix).
* **Pipeline Checks:**
  1. Formatter / Linter validation (`pnpm check` and `golangci-lint run`).
  2. Frontend unit tests execution (`pnpm test`).
  3. Backend unit tests execution with race detection (`go test -v -race ./...`).
